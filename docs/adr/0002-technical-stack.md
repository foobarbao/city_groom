# ADR-0002 — Technical stack

- **Status**: Accepted
- **Date**: 2026-10-24 (revised the same day as requirements were clarified)

## Context

- **Need**: a platform connecting residents of the Grenoble area with
  city-centre service businesses (laundry, shoe repair, repairs…) through
  **connected lockers**. The demo is built around a **real map of Grenoble**,
  **simulated lockers** and **real shops**, with as much real data as possible.
  See [`docs/PRODUCT.md`](../PRODUCT.md).
- Three user interfaces are needed:
  1. a **customer app** (mobile: Android APK + installable web app);
  2. a **merchant portal** (web, desktop-first): incoming orders, forecasts,
     revenue and commission;
  3. an **administration interface** (web) for the project owner to manage all
     data, with a real backend able to connect real lockers later.
- The demo must be easy to distribute to testers, then serve as the foundation
  for production.
- The project owner is an expert in **Vue.js** and **Django REST**, with no
  mobile experience.
- The core of the product is **geographic**: proximity search, radius, zones,
  courier rounds. Spatial storage and queries are a major selection criterion.
- The project owner delegated the stack choice with the criterion "the most
  relevant option for the project".

## Options considered

### Customer app

1. **Vue 3 + Ionic + Capacitor** — Reuses Vue skills directly. One codebase
   produces a PWA and an APK (and iOS later). Ionic provides mobile-like
   navigation (page transitions, Android back button). Capacitor gives access
   to native features (GPS, notifications, QR code scanning to open a locker)
   with web fallbacks. A web map (MapLibre) works as-is.
2. **Vue 3 + Quasar + Capacitor** — Same strengths, less "native" navigation by
   default.
3. **Flutter / React Native** — More native rendering, but a new language or
   framework to learn, a less mature or costlier web version, and a separate
   map integration for web and mobile.
4. **Native Kotlin** — No web version, no iOS, steepest learning curve.

### Map

1. **MapLibre GL JS + OpenStreetMap vector tiles** — Open source, no key or
   account, smooth vector rendering, customisable styles. OSM data is very rich
   in Grenoble.
2. **Leaflet + raster tiles** — Simpler, but less fluid on mobile and less
   customisable.
3. **Google Maps / Mapbox** — Excellent, but account, key and usage-based
   billing; commercial dependency from day one.

### Backend

1. **Django REST Framework + GeoDjango + PostgreSQL/PostGIS** — Existing
   skills. GeoDjango and PostGIS provide spatial queries natively (distance,
   radius, polygons), and `djangorestframework-gis` serialises to GeoJSON,
   directly consumable by MapLibre. The Django admin provides a full
   administration interface out of the box. The locker simulator can run as a
   scheduled task on the server.
2. **No backend (static JSON in the app)** — Faster for a mock-up, but
   everything would have to be redone for production (locker state, orders,
   accounts, merchant portal).
3. **BaaS (Firebase, Supabase)** — Fast, but new skills to acquire and vendor
   lock-in for production.

## Decision

| Layer | Choice |
|---|---|
| Customer app | **Vue 3 + TypeScript + Ionic Vue + Capacitor**, built with **Vite** |
| Merchant portal | **Vue 3 + TypeScript + Vite** (web, desktop-first) |
| Administration | **Django admin**, customised (see ADR-0003) |
| State, routing, i18n | Pinia, Vue Router, vue-i18n (`fr` locale) |
| Map | **MapLibre GL JS**, OpenStreetMap-based vector tiles |
| Backend | **Django + Django REST Framework + GeoDjango**, OpenAPI schema generated from the code |
| Database | **PostgreSQL + PostGIS** |
| Tests | Vitest, Vue Test Utils, Playwright (frontends); pytest (backend) |
| Quality | ESLint, Prettier (frontends); Ruff + a type checker (backend) |
| Local environment | Docker Compose (PostgreSQL/PostGIS + backend) |

Distribution of the customer app:

- **PWA** deployed at a URL for broad testing;
- **APK** generated by Capacitor for testers who need native features, then
  **AAB** for the Play Store.

Exact tool versions are pinned when the project is initialised, after checking
the current stable versions and their mutual compatibility (Capacitor, Ionic
Vue, Node, Android Studio, Django, Python), and recorded in the README.

## Consequences

- Minimal learning curve: Vue on the frontends, Django on the server; the only
  new topics are Capacitor, the Android build and cartography.
- Native features are abstracted behind services (see `CODING_STANDARDS.md`
  §7) so the PWA works without them or with a fallback.
- **Tile provider**: openstreetmap.org tile servers forbid heavy use by a
  distributed app without prior permission; they will not be used. For the
  demo, a free OSM-based vector tile service with no key (e.g. OpenFreeMap) is
  considered. Such services come with no guarantee, so the tile URL is
  configurable through an environment variable, and self-hosting tiles is
  planned for production (`PROD:`). Final choice recorded in
  `docs/DATA_SOURCES.md`.
- **OpenStreetMap attribution is mandatory** on every map (ODbL licence).
- The Android build requires Android Studio / the Android SDK and a JDK; the
  procedure will be described in `docs/BUILD_AND_RELEASE.md`.
- A signing keystore must be created and backed up outside the repository
  before the first APK is distributed.
- Hosting for the backend and a PostGIS database is needed as soon as the demo
  is distributed (see ADR-0004).
